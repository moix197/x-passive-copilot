# sync-knowledge

The single owner of the **procedure** for writing and maintaining `.ai/`. The
**format** — layout, frontmatter schema, read protocol — is owned by
`.ai/README.md`; read it before writing and do not restate it elsewhere. Both
`write-prd` (which declares a plan's `## Knowledge Base Impact`) and `execute-prd`
(which calls this at closeout) defer to the rules here.

`.ai/` exists so agents retrieve the **map and the decisions** instead of
re-deriving the codebase from source every research pass. One file is one
retrievable chunk, so it only works if entries stay small, current, and
decision-oriented.

## The rule: decision-oriented, not a wiki

> `.ai/` captures **decisions, constraints, invariants, and the map of where
> things live** — the non-obvious *why*. It does NOT restate what the code does.
> If a doc could be regenerated by reading the code, it doesn't belong here.

The test for any entry: *"Could a competent reader reconstruct this by reading
the code?"* If yes, leave it out. Echoing CLAUDE.md: no speculative content, no
dead entries, no comments that restate the code — only the non-obvious *why*.

**Prefer editing or retiring over appending.** The default failure mode of a
knowledge base is unbounded growth. When a change supersedes an entry, rewrite,
supersede, or delete it — never stack a new note or a changelog on the stale one.

## Writing an entry

An entry is `.ai/<domain>/<slug>.md` and answers **one question**. Frontmatter is
strict and flat (full schema and enums: `.ai/README.md`):

```markdown
---
id: auth/session-cookie-only
type: decision
summary: Sessions live in an httpOnly cookie, never localStorage, so XSS cannot read tokens.
tags: [session, cookies]
paths: [packages/auth/**]
related: [architecture/dependency-direction]
status: active
updated: 2026-01-31
---
```

- **Domain** — the folder is *what you're working on* (`architecture`, `auth`,
  `data`, `ui`, `tooling`…), never the entry type. Pick the domain whose `scope:`
  someone doing this work would open first; system-wide shape goes in
  `architecture/`. Create a new domain (folder + `index.md` with a one-line
  `scope:` and the entry markers) only when no existing scope fits.
- **Type** — `decision | pattern | constraint | gotcha | howto | map`. `pattern`
  only on the **2nd real use**, never speculatively.
- **Summary** — the retrieval key, one line ≤160 chars. State the *answer*, not
  the topic: "Packages depend downward only; shared code is extracted, never
  cross-imported", not "Notes on package dependencies".
- **Paths / tags** — `paths` are repo-relative globs of the code concerned (may
  be `[]`); they are how the next sync finds this entry. Tags are kebab-case.
- **Split** when the body nears the 80-line cap, when the summary needs an "and"
  to be true, or when two parts would be retrieved by different tasks. Link the
  halves through `related`.

`decision` entries use this body, kept short:

```markdown
# <Decision title>

**Decision:** <what was chosen, one or two sentences>

**Why:** <the non-obvious reasoning — constraints, trade-offs that forced it>

**Rejected:** <the alternatives considered and why they lost>

**Constraints it creates:** <invariants future code must respect, if any>
```

Record a decision only when the *why* isn't obvious from the code. A routine,
self-evident choice does not need a record.

## Sync routine (manual or called by execute-prd)

Given a completed change (and, when available, the plan's `## Knowledge Base
Impact` section as the starting checklist):

1. **Locate `.ai/` and identify what changed.** If `.ai/` doesn't exist, there's
   nothing to sync — report that and stop. Otherwise list the concepts, modules,
   flows, and decisions the change introduced, altered, or removed, plus the
   paths it touched.
2. **Find affected entries through the indexes.** Read `.ai/index.md`, then only
   the relevant `<domain>/index.md` tables, and match rows by `paths`, tags, and
   summary. Open only the matches — never bulk-read a domain folder.
3. **Retire what's now stale.** Subject gone: delete the file and fix `related`
   refs pointing at it. Replaced but the history still explains live code: write
   the new entry and mark the old one `status: superseded` + `superseded_by`.
   This step matters more than adding — it's what keeps `.ai/` from becoming a
   wiki.
4. **Edit or add.** Prefer editing an existing entry in place (bump `updated`).
   Add a new atomic entry only for a genuinely new question, per "Writing an
   entry" above. Apply the anti-wiki test to everything you wrote: delete
   anything that merely restates code.
5. **Regenerate and lint.** Run `node .ai/_tools/build-index.mjs`, then
   `node .ai/_tools/build-index.mjs --check`. Fix every lint error in the entries
   and re-run until `--check` exits 0. Never hand-edit a generated index region;
   only a domain index's `scope:` and intro are hand-written.
6. **Report** the entry ids added / edited / superseded / retired, one line each.

When invoked from `execute-prd`, perform this **inside the plan's worktree,
before merge approval**, so the `.ai/` changes ship with (and are approved
with) the code. Commit there as `docs(ai): sync knowledge base [<slug>]` and
hand the list of touched entries back for the approval request.

## Bootstrap (first run on an existing codebase)

Triggers: "/sync-knowledge bootstrap", "seed the knowledge base", or a sync
where `.ai/` holds only the starter `tooling/knowledge-base-layout` entry while
the repo already has code. Goal: the **10–30 most useful entries**, not
coverage. The anti-wiki rule applies with full force.

1. **Map the repo with read-only subagents** — one per top-level area (each
   app/package/major `src/` folder), `model: haiku` for structure and
   manifests, `sonnet` where judging decisions is needed. Each replies in
   ≤300 words: the area's responsibility, entry points, boundaries and
   dependency direction, plus non-obvious decisions / constraints / gotchas
   **with evidence** (file:line, README, ADR, commit message, a comment
   explaining *why*).
2. **Propose before writing.** Show the user one table: domain (with its
   one-line `scope:`), entry id, type, summary. Prefer `map` entries for where
   things live and how areas connect; `decision` / `constraint` / `gotcha`
   only with evidence. Wait for a yes or edits.
3. **Never invent the why.** If the reason for a choice isn't in code, docs or
   history, ask the user or leave the entry out — a guessed rationale is worse
   than none.
4. **Write the entries** per "Writing an entry", creating each domain folder +
   `index.md` (`scope:` + entry markers). Set `updated` to today.
5. **Regenerate and lint** (`node .ai/_tools/build-index.mjs`, then `--check`)
   until clean, then report the domains and entry ids created. Commit only if
   the user asks.
